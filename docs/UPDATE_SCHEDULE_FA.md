# به‌روزرسانیِ دوره‌ای (هر یک ساعت) — چطور و چرا

تاریخ: ۳۱ شهریور ۱۴۰۵ · هدف: هیچ جلسه‌یِ بازاری بدون انتشار نماند.

---

## ۱) مسئله، با عدد نه حدس

زمان‌بندیِ cron گیت‌هاب **«بهترین تلاش»** است و برای cronهای پرتکرار (مثل `*/15`)
در عمل فقط چند بار در روز اجرا می‌شود. نمونه‌ی مستند از همین مخزن:

| زمان (UTC) | رویداد |
|---|---|
| ۰۵:۳۰–۰۹:۰۰ | **جلسه‌ی بورس تهران باز است** |
| — | هیچ اجرایی از جریانِ انتشار در این بازه رخ نداد |
| ۱۰:۴۴ | اولین انتشارِ روز؛ جلسه بسته شده بود |

نتیجه: داده‌ی بورس تا فردا عقب ماند و «ورود و خروجِ پولِ امروز» اصلاً اندازه‌گیری نشد
(جزئیات در [`docs/MONEYFLOW_FA.md`](./MONEYFLOW_FA.md)).

نکته‌ی مهم: این تقصیرِ تنظیمات نبود — **تعدادِ cron را زیاد کردن هم مشکل را حل نمی‌کند**،
چون گیت‌هاب در زمانِ شلوغی اجراها را می‌اندازد. باید ساختار را عوض کرد، نه تعداد را.

## ۲) معماری: چهار لایه

```
۱) ضربانِ ساعتی      cron روی دقیقه‌ی ۵ و ۳۵ هر ساعت      → اگر یک ضربان پرید، دیگری هست
۲) حلقه‌ی درون‌کار    هر اجرا ۲ دور با فاصله‌ی ۴۵ دقیقه    → یک اجرا ۴۵ دقیقه‌ی آینده را هم می‌پوشاند
۳) نگهبانِ ساعتی     یک کارِ بلندمدت، ۶ دورِ یک‌ساعته      → یک بار بیدار شدن = ۵ ساعت پوشش
۴) کرونِ بیرونی      repository_dispatch (اختیاری)        → دقیق‌ترین حالت: هر ساعت از یک سرویسِ رایگان
```

| لایه | فایل | پیش‌فرض | چطور تنظیمش کنی |
|---|---|---|---|
| ضربانِ ساعتی | `.github/workflows/publisher.yml` | `cron: '5 * * * *'` و `'35 * * * *'` (کنارِ `*/15`) | همان فایل |
| حلقه‌ی درون‌کار | `scripts/publish_rounds.sh` | `ROUNDS=2`، `INTERVAL_MIN=45` | `workflow_dispatch` یا تغییرِ `env` در فایل |
| نگهبانِ ساعتی | `.github/workflows/hourly.yml` | هر ۶ ساعت بیدار می‌شود، ۶ دورِ ساعتی | متغیرِ `ROUNDS` در اجرای دستی |
| کرونِ بیرونی | همان `publisher.yml` | خاموش | پایین را ببین |

هر چهار لایه **یک اسکریپت** را صدا می‌زنند (`scripts/publish_rounds.sh`) تا منطقِ
«همگام‌سازی + انتشار + کامیتِ ایمن» یک‌جا بماند و دو جریان از هم جدا نیفتند.

### مهارِ تداخل

دو جریانِ هم‌زمان نباید دوباره منتشر کنند:

```bash
node scripts/publish.cjs --min-gap=20
```

اگر `live.json` از ۲۰ دقیقه تازه‌تر باشد، اجرا **هیچ واکشی و هیچ کامیتی** نمی‌کند و
فقط یک خط می‌نویسد. نگهبانِ ساعتی از `--min-gap=40` استفاده می‌کند.

## ۳) لایه‌ی چهارم: یک کرونِ بیرونیِ رایگان (اختیاری)

دقیق‌ترین راه برای «هر ساعت، سرِ ساعت» این است که یک سرویسِ رایگانِ زمان‌بندی،
این جریان را صدا بزند. هر سرویسی که بتواند یک درخواستِ HTTP بفرستد کار می‌کند
(cron-job.org، UptimeRobot، Cloudflare Workers Cron، یا یک سرورِ خانگی).

```bash
curl -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer <TOKEN-with-repo:actions>" \
  https://api.github.com/repos/AliB11/Garmasanj-Eghtesad/dispatches \
  -d '{"event_type":"publish"}'
```

> توکن را در **Settings → Developer settings → Personal access tokens** با دسترسیِ
> `actions:write` روی همین مخزن بساز. اگر ترجیح می‌دهی هیچ توکنی نسازی، لایه‌های
> ۱ تا ۳ کافی‌اند (فقط با دقتِ کمتر).

## ۴) چه چیزی هر ساعت تازه می‌شود؟

| داده | منبع | شرطِ تازه‌شدن |
|---|---|---|
| ۲۰ کوت (ارز، طلا، سکه، رمزارز) | TGJU + صرافی‌ها + جهانی | هر انتشار |
| شاخصِ کلِ بورس | TGJU | هر انتشار |
| مکملِ بورس (هم‌وزن، فرابورس، صندوق‌ها، پهنا، صف‌ها) | bourse-trader.ir | **فقط در ساعتِ بازارِ تهران**، با فاصله‌ی حداقل ۳۰ دقیقه |
| جریانِ پولِ حقیقی + ارزشِ صف‌ها | همان | همان؛ و بعد از بسته‌شدن، «حفظِ جلسه» می‌شود |
| روندِ پول در جلسه | انباشته از انتشارها | هر انتشاری که در جلسه باشد، یک نقطه می‌افزاید |
| تاریخچه (`history.json`) | — | هر انتشار یک نقطه |

خارج از ساعتِ بازار، ناشر صفحه‌یِ بورس‌تریدر را **نمی‌خواند** (ادب) و همان مقدارِ قبلی را
نگه می‌دارد؛ ردیفِ «سلامت داده» می‌گوید «بیرون از ساعتِ بازار».

## ۵) متغیرهای قابلِ تنظیم

| متغیر | پیش‌فرض | معنا |
|---|---|---|
| `ROUNDS` | ۲ (ناشر) / ۶ (نگهبان) | تعدادِ دورِ انتشار در یک اجرا |
| `INTERVAL_MIN` | ۴۵ (ناشر) / ۶۰ (نگهبان) | فاصله‌یِ بینِ دو دور |
| `MIN_GAP_MIN` | ۲۰ (ناشر) / ۴۰ (نگهبان) | اگر انتشار از این حد تازه‌تر باشد، این دور کاری نمی‌کند |
| `BT_MIN_GAP_MIN` | ۳۰ | فاصله‌یِ واکشیِ صفحه‌یِ عمومیِ بورس‌تریدر (کمتر از ۱۵ پذیرفته نمی‌شود) |
| `vars.HOURLY_KEEPER` | (نبودن = روشن) | مقدارِ `false` نگهبانِ ساعتی را خاموش می‌کند |

نگهبانِ ساعتی یک رانر را حدود ۵ ساعت نگه می‌دارد (۴ بار در شبانه‌روز ≈ ۲۰ ساعت در روز).
روی مخزنِ عمومی هزینه‌ای ندارد، اما اگر نمی‌خواهی:

```
Settings → Secrets and variables → Actions → Variables → New repository variable
Name: HOURLY_KEEPER   Value: false
```

## ۶) چطور بفهمی کار می‌کند؟

```bash
# آخرین انتشار چند دقیقه پیش بوده؟
node -e "const j=require('./assets/data/live.json');
const m=(Date.now()-Date.parse(j.generated_at))/60000;
console.log(j.generated_fa, '|', m.toFixed(1), 'دقیقه پیش | منابعِ سالم:',
  Object.values(j.meta.sources).filter(s=>s.ok).length)"

# چند انتشار امروز داشتیم؟
git log --since='24 hours ago' --oneline -- assets/data/live.json | wc -l
```

و در تبِ **Actions**：دو جریانِ «انتشار زنده قیمت‌ها» و «نگهبان ساعتی انتشار».

## ۷) اگر باز هم وقفه افتاد

۱. تبِ Actions را باز کن: اگر جریان‌ها **queued** مانده‌اند، یعنی cron عقب است (صبر کن؛
   حلقه‌ی درون‌کار خودش جبران می‌کند).
۲. اگر `push failed after 3 attempts` دیدی: تداخلِ دو جریان است؛ دورِ بعد با
   `git pull --rebase` خودبه‌خود درست می‌شود (منطق در `publish_rounds.sh`).
۳. اگر `PUBLISH ABORT: core incomplete` دیدی: منبعی پاسخ نداده و سامانه عمداً
   **چیزی منتشر نکرده** (عددِ ناقص بدتر از عددِ کهنه است).
